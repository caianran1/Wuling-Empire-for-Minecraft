### 关于「灵珠种类决定修炼方向」

**这是本次改动里最需要你确认的一点。**

第一部原文只定义了五种**品质**，没有「种类」。但第四部物价写的是  
「极品**僵尸**灵珠」「极品**骷髅**灵珠」「极品**恶魂**灵珠」，  
第二部又说「种类决定修炼方向」——所以灵珠必然还有**来源生物**这一维度。

我的处理：给灵珠物品加了 NBT 字段 `Source`，记录掉落它的怪物 ID。  
怪物死亡时写入，捡起后保留，tooltip 上显示。

&#x4F46;**「来源 → 修炼方向」的映射表原文没给**，目前实现是：  
所有来源共享同一份武灵候选表，按你确认的稀有度权重（1/100 vs 1/10）抽取。  
等这份映射表明确了，改 `WuLingType.roll` 一处即可，不用动其他逻辑。

## 二、等级体系

```
木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石
 ↓
每个大境界内部：前期 → 中期 → 后期
```

总索引 = 大境界序号 × 3 + 小境界序号，取值 **0 ~ 20**，共 21 个台阶。

### 小境界晋升（前 → 中 → 后）

无需渡劫、无需物资，纯粹累积修炼进度：

```
每晋升一个小境界所需进度 = thresholdBase × thresholdGrowth ^ 大境界序号
```

默认 `thresholdBase = 120`、`thresholdGrowth = 2.2`：

| 大境界  | 晋升一次所需进度 |
| ---- | -------- |
| 木    | 120      |
| 石    | 264      |
| 黄金   | 581      |
| 玄铁   | 1,278    |
| 钻石   | 2,811    |
| 下界合金 | 6,184    |
| 绿宝石  | 13,606   |

**后期不会自动跨到大境界**——这是原文定的规则，大境界必须走突破流程。

### 修炼动作与进度产出

| 动作   | 默认每次产出  | 适用武灵     |
| ---- | ------- | -------- |
| 造成伤害 | 1 × 伤害值 | 剑、斧、火    |
| 挖掘方块 | 1       | 斧、镐、铲    |
| 弓箭命中 | 6       | 弓        |
| 承受伤害 | 2       | 盔甲、水     |
| 使用道具 | 4       | 水、火、红石、书 |

**关键约束**：只有「真的在使用自己的武灵」才计数。  
剑武灵要求手里拿的是剑（`ItemTags.SWORDS`），镐武灵要求拿镐，  
弓武灵要求拿弓/弩，盔甲武灵要求身上穿着盔甲。水/火/红石/书不限制手持。

## 三、开启、境界上限与修炼速度

### 操作方式

| 操作             | 效果                                   |
| -------------- | ------------------------------------ |
| **Shift + M**  | 凝聚出实体武灵（不需要绑定器，消耗灵力）；**书武灵例外 → 打开附魔书凝聚界面（0.3.2）** |
| **Shift + N**  | 打开武灵升级面板（不需要绑定器，0.2.20）              |
| **手持灵珠右键村民牧师** | 请牧师开启武灵 —— 种类**由牧师抽取**，玩家不能选（0.2.21） |
| 绑定器 Shift + 右键 | 打开武灵选择界面（选种类并绑定）                     |
| 绑定器 右键         | 打开武灵升级面板（快捷键的等价入口）                   |

**种类由玩家自己选**，不是随机。按下后会弹出 `WuLingChooseScreen`，  
十种武灵两列排开，各自标注原文给的稀有度（稀有 1/100、常见 1/10）作为参考信息。  
选定后客户端把种类 key 发给服务端，服务端校验物资并写入。

> 注意：既然改为自选，原文的 1/100 与 1/10 就不再是「抽取概率」，  
> 只作为稀有度的展示标签保留。如果后续希望稀有种类有额外门槛  
> （例如极品灵珠才能选剑），在 `WuLingBinding` 里加一道校验即可。

本地会先粗校验一次：身上有没有绑定器、有没有灵珠，  
不满足直接给提示，不必弹界面。最终判定仍然在服务端。

Shift + M 与 Shift + N 都走 `ModKeyMappings`（默认 M / N 键，归入「武灵帝国」按键分类）。  
1.20.1 的 `KeyMapping` 不支持修饰键，所以两个键都由按键映射注册，  
Shift 在 `ClientTickHandler` 里用 `InputConstants.isKeyDown` 额外判断——  
只按 N 提示「打开武灵面板需要按住 Shift」，**只按 M 则完全静默**（0.4.2 起，见下），都不会误触发。

> **0.4.2 凝聚提示精简（用户要求）**：`Shift+M` 凝聚**不再往聊天栏发任何消息** ——
> 既没有「没按住 Shift」的提醒（未按 Shift 按 M 直接忽略），也没有凝聚成功的回执。
> 反馈只靠掉落物实体 + 升级音效 + 右上角 HUD 灵力条。`Shift+N` / `Shift+P` 的提醒**保留**。

两个快捷键都**不需要携带武灵绑定器**（0.2.14 起凝聚、0.2.20 起开面板）。  
面板本身是纯客户端界面，数据由服务端的 `WuLingSyncPacket` 推送，因此打开时无需发包。

#### 凝聚（Shift + M）的 0.2.14 口径

| 项       | 口径                                              |
| ------- | ----------------------------------------------- |
| 是否需要绑定器 | **不需要**（绑定器只管开武灵 / 选种类 / 开面板）                   |
| 是否消耗灵珠  | 不需要                                             |
| 是否消耗灵力  | **需要**，一次 `condenseSpiritCost`（默认 25，百分制）；不足则拒绝 |
| 例外      | 创造绑定器绑定后自动送的那一次**免费**                           |

绑定（选种类）仍然需要背包里有绑定器 + 至少一颗灵珠，  
灵珠取用顺序：副手 → 主手 → 背包自上而下。

#### 附魔书凝聚界面（0.3.2）

**只对书武灵生效。** 其余武灵的 Shift+M 是「按下去就掉实物」，但书武灵的实物是
一本附魔书 —— 附魔与等级都得玩家说了算，所以这一档改成先开界面：

| 项 | 口径 |
| --- | --- |
| 入口 | 书武灵状态下按 **Shift + M**（`ClientTickHandler` 里按 `ClientWuLingData.type() == BOOK` 分流） |
| 界面 | `client/WuLingBookScreen`，纯手写渲染 + 自算命中区（不用 `ObjectSelectionList`） |
| 内容 | 列出 `ForgeRegistries.ENCHANTMENTS` 里**全部**附魔，按本地化名排序；每行 `−` / 等级 / `+` / 「凝聚」 |
| 等级范围 | `1 ~ 该附魔的 getMaxLevel()`，**不按境界设限**（用户口径：「创造模式的那一类」＝自由挑） |
| 消耗 | **随附魔稀有度与等级递增**（0.3.5）—— 见下方公式；不封顶高等级书会做不出来 |
| 物品 | 仍是本境界那件 `<境界>_书`（`ManifestItems.single(realm, BOOK)`），只是把默认的耐久换成玩家选的附魔 |
| 发包 | `WuLingBookPacket(enchantId, level)` → 服务端 `WuLingBinding#condenseBook` |
| 服务端复判 | 是否已开启武灵、是不是书武灵、灵力够不够、等级再夹一次 `[1, maxLevel]` |

**消耗公式（0.3.5，用户口径「附魔书凝聚等级越高，附魔书越稀有消耗越大」）**

```
消耗 = condenseSpiritCost × 稀有度倍率 × (1 + bookCostPerLevel × (等级 − 1))，最后封顶到灵力上限
```

| 配置键 | 默认 | 含义 |
| --- | --- | --- |
| `bookCostPerLevel` | 0.5 | 每高 1 级再 +50%（2 级 ×1.5、3 级 ×2.0、5 级 ×3.0） |
| `bookRarityCommon` | 1.0 | 普通附魔倍率 |
| `bookRarityUncommon` | 1.5 | 少见附魔倍率 |
| `bookRarityRare` | 2.5 | 稀有附魔倍率（经验修补、冰霜行者…） |
| `bookRarityVeryRare` | 4.0 | 极稀有附魔倍率（无限、灵魂疾行…） |

默认值（基础 25）下的参考消耗：

| 附魔书 | 稀有度 | 消耗 |
| --- | --- | --- |
| 耐久 III | 普通 | 50 |
| 保护 IV | 普通 | 62.5 |
| 锋利 V | 普通 | 75 |
| 经验修补 I | 稀有 | 62.5 |
| 无限 I | 极稀有 | 100（封顶） |

⚠️ **必须封顶到灵力上限**：灵力上限默认只有 100，极稀有 × 高等级那几个组合的
原始值会超过上限，不封顶就等于这些书被永久锁死（灵力顶满也点不动）。

计算收口在 `wuling/BookCost`，**客户端界面与服务端判定共用同一份**（否则界面显示的
数字与实际扣的不一致）。界面上每行的消耗数字实时随等级变化，灵力不够时标红。

⚠️ **自选附魔书必须记 NBT**（`ManifestItems` 的 `TAG_BOOK_ENCHANT` / `TAG_BOOK_LEVEL`）：
境界提升时 `WuLingBinding#refreshManifestItems` 会把旧件换成新境界的那件，
不还原附魔的话，玩家挑的附魔会被冲成 `applyManifestEnchants` 给的默认「耐久」。
`refreshManifestItems` 里因此多了一段「先 clear 默认附魔，再按记录还原」。

### 村民牧师：抽取开启武灵（0.2.21）

> 原文口径：「给村民牧师加入武灵开启的技能（是抽取而不是选择）」

| 项      | 口径                                                                              |
| ------ | ------------------------------------------------------------------------------- |
| 触发     | **手持灵珠右键村民牧师**（空手右键仍是原版交易）                                                      |
| 与交易的关系 | 只要手里拿着灵珠，这次右键就被牧师接管，不会弹出交易界面；没拿灵珠完全不干涉                                          |
| 谁能开    | 只有职业 = `minecraft:cleric`（牧师）的村民；其它职业无效                                         |
| 种类     | **抽取**，走 `WuLingType.roll`：剑 / 弓 / 水 / 火 / 书 各 1 份权重，斧 / 镐 / 铲 / 红石 / 盔甲 各 10 份 |
| 修炼速度   | 由**你交出去的那颗灵珠**品质决定（凡品 ×1 → 极品 ×3），见下方表格；**上限与品质无关**                             |
| 消耗     | 手里那叠灵珠扣 `bindingBeadCount`（默认 1 颗）；不需要武灵绑定器                                     |
| 重复开启   | 已拥有武灵时拒绝（牧师摇头 + 冒火），要换先 `/wuling spirit unbind`                                 |
| 表现     | 附魔台音效 + 牧师「嗯哼」+ 玩家升级音 + `ENCHANT` 符文粒子 + 绿色村民粒子                                 |

**这就是生存玩家开启武灵的正路**：绑定器是「仅限创造模式取得」的物品（原文设定），  
所以生存里只能请牧师抽签；想自己挑种类只能开创造拿绑定器。

代码入口：`ModEvents#onClericOpenWuLing`（判定职业、决定是否吞掉原版交互）  
→ `WuLingBinding#openByNpc`（真正的绑定与消耗）。

### 品质 → 修炼速度（0.2.22 口径）

> 用户原话：「品质上限不由你交出去的那颗灵珠决定，所有都一样的上限，  
> 只是修炼的速度加成不一样」

| 项    | 口径                                                                      |
| ---- | ----------------------------------------------------------------------- |
| 境界上限 | **人人相同**，一律到 `Config.maxRealm`（默认 6 = 绿宝石·后期）。凡品灵珠开出来的武灵照样能修到绿宝石        |
| 灵珠品质 | **只决定修炼速度倍率**，即每次修炼动作累积的进度乘几倍                                           |
| 触发处  | `WuLingData#addProgress` 里 `progress += amount * cultivationBonus`，一处收口 |
| 表现   | 灵珠 tooltip 多一行「修炼速度 ×N」；升级面板显示「修炼速度 ×N（上限人人相同）」                         |
| 创造成本 | 创造绑定器不消耗灵珠 → 无品质加成，按 ×1 开启                                              |

| 灵珠品质 | 修炼速度加成（`cultivationBonus*`） | 攒满同一档进度的相对耗时 |
| ---- | --------------------------- | ------------ |
| 凡品   | ×1.0（基准）                    | 1.00         |
| 良品   | ×1.25                       | 0.80         |
| 优品   | ×1.5                        | 0.67         |
| 上品   | ×2.0                        | 0.50         |
| 极品   | ×3.0                        | 0.33         |

倍率可在 `Config.cultivationBonusFan ~ cultivationBonusJi` 里调。  
（2026-09-27 之前的旧存档没有这个字段，读入时按 ×1.0 处理 —— 想拿加成可以重开一次武灵。）

> 注：配置键从旧的 `capFan ~ capJi` 换成了 `maxRealm` + `cultivationBonus*`。  
> 老配置文件里的旧键仍然存在但**不再被读取**，这是故意的 ——  
> Forge 不会把已生成的配置跟随代码默认值更新，沿用旧键名会出现「改了却没生效」的假象。

## 四、大境界突破流程

```
已开启武灵，且处于当前大境界的「后期」
        │
        ├─ 未达后期      → 提示「需先修炼到后期」
        ├─ 触及统一上限  → 提示上限境界（人人相同），拒绝
        ├─ 物资不足      → 提示「物资不足」
        ▼
  扣除全部物资 → 境界 +1（小境界归零）→ 推送新数据
```

> **突破与灵力完全无关**（0.2.15 起）：  
> 既不消耗灵力，也不要求灵力圆满（旧的「灵力满 100% 才能突破」门槛已删除）。  
> 灵力只与「凝聚武灵」挂钩 —— `condenseSpiritCost` 默认 25（百分制），不足则无法凝聚。  
> `breakthroughConsumesSpirit` 默认 `false`；配置键由旧的 `breakthroughClearsSpirit` 改名而来，  
> 免得老配置文件里的 `true` 继续生效。

### 凝聚出的武灵比原版强多少（0.2.14 起；0.2.26 改为「每档碾压上一档」）

`WuLingType#empower` 会在凝聚时给物品**额外挂一条属性修饰符**（写在物品 NBT 上，  
原版换装备时会自动重新计算，见 `LivingEntity#handleEquipmentChanges`）：

**最终数值 = 该物品原版同款的数值 × 境界倍数**（配置默认 100% 时）

实现上挂出去的修饰符 = 原版数值 × (境界倍数 − 1) × 配置百分比。  
（攻击力另加玩家自身的基础攻击力 1 一起算，因为原版 tooltip 上的「木剑 4」= 修正值 3 + 这 1 点。）

| 配置项                   | 默认  | 效果                                    |
| --------------------- | --- | ------------------------------------- |
| `manifestAttackBonus` | 100 | 剑/斧/镐/铲：按原版攻击力百分比追加，再乘 (境界倍数 − 1)     |
| `manifestArmorBonus`  | 100 | 盔甲：按原版护甲值 / 韧性百分比追加，再乘 (境界倍数 − 1)     |
| `manifestStageStep`   | 0.1 | 每提升一个小境界额外 +10%（2026-10-02 起，0 = 小境界不影响属性） |

**境界倍数**（`WuLingRealm#manifestMultiplier`）

| 境界   | 大境界倍数  | 剑：前期 → 中期 → 后期（小境界 +10%/级）  | 相邻大境界 |
| ---- | ------ | --------------------------- | ----- |
| 木    | 3      | 12 → 13.2 → 14.4            | —     |
| 石    | 4      | 20 → 22 → 24                | 1.67× |
| 黄金   | 8      | 32 → 35.2 → 38.4            | 1.60× |
| 玄铁   | 9      | 54 → 59.4 → 64.8            | 1.69× |
| 钻石   | 11     | 77 → 84.7 → 92.4            | 1.43× |
| 下界合金 | 14     | 112 → 123.2 → 134.4         | 1.45× |
| 绿宝石  | **15** | 240 → 264 → **288**         | 2.14× |

**每一档都严格碾压上一档（≥1.43 倍）；同一大境界内每升一个小境界也涨 10%**
（2026-10-02「每升一等级基础属性都会提升」，`WuLingRealm#manifestMultiplier(int)`）。
小境界只乘系数、不改大境界基准，所以大境界之间的断层不受影响。

> 小境界升级时物品<b>还是同一件</b>（`wood_sword` 仍是 `wood_sword`），
> 靠物品 NBT 上的 `WuLingManifestStage` 记「这一件是在哪个小境界凝聚的」来判断要不要重算属性；
> 重算时把**耐久 / 附魔 / 自定义名**原样搬过去，所以既不白刷耐久，也不会吞掉玩家自己加的附魔。
> 大境界突破换的是另一件物品，仍是整件替换（自选附魔书按 NBT 还原）。

- **为什么倍数不是等比的（黄金 8 > 石 4，玄铁 9 却只比黄金多 1）**：  
  原版各材质的底子**不是等差**的——剑的伤害是 木 4、石 5、**金 4（比石剑还低）**、  
  玄铁 6、钻石 7、下界合金 8，绿宝石是单独设计的物品 16。要让**实际数值**成阶梯，  
  倍数就得按底子补偿：黄金档必须给到 8，否则会出现「黄金境界不如石境界」的倒挂。  
  （金甲的原版韧性为 0，所以黄金档只有护甲值加成，没有韧性加成。）
- **工具类的挖掘速度**：原版没有「挖掘速度」属性/修饰符，只有 `Tier#getSpeed`，  
  所以 0.2.25 起斧 / 镐 / 铲按境界附赠**效率附魔** `min(境界序号+1, 5)`  
  （木 效率 I → 钻石及以上 效率 V），让低境界工具在挖掘上也强于原版同款。
- 绿宝石境界各件凝聚物的实际表现（配置默认 100%，倍数 15）：
  | 种类 | 基础（含材质伤害档）      | 武灵之力追加 | 附魔      | 合计                       |
  | -- | --------------- | ------ | ------- | ------------------------ |
  | 剑  | 16              | +224   | 锋利 V +3 | **243**                  |
  | 斧  | 18              | +252   | —       | **270**                  |
  | 镐  | 14              | +196   | —       | **210**                  |
  | 铲  | 14.5            | +203   | —       | **217.5**                |
  | 胸甲 | 护甲 16 / 韧性 12   | 护甲 +224 / 韧性 +168 | — | 护甲 **240** / 韧性 **180** |
  对比：钻石境界的钻石剑 **77**、下界合金境界 **112** ——  
  绿宝石剑（243 含附魔）是钻石境界的 **3.2 倍**、下界合金境界的 **2.2 倍**、  
  原版钻石剑（7）的 **35 倍**，一击即可秒杀满血末影龙（200 血）。
- 没有对应属性的（弓、水/火/红石/书）自然跳过；弓的强化仍靠随境界加的**力量附魔**。
- 物品 tooltip 里会多一行「武灵之力：攻击力额外 +N」，方便核对。

> 想把整体强度压回来：`manifestAttackBonus` / `manifestArmorBonus` 各改小即可  
> （倍数是代码常量、配置是全局乘数）。要让某一件单独更强，在 `WuLingType#manifest`  
> 里加一条分支，单独传一个倍数给 `empower`。

**为什么护甲值只给 2 倍**：原版减伤公式把有效护甲 clamp 到 20 点  
（`CombatRules#getDamageAfterAbsorb`），所以「护甲堆到 40」的价值不在面板数字，  
而在**扛大伤害**——高护甲 + 高韧性能让一次 40 点重击的减伤从钻石套的 16% 提到 **80%**。

**⚠️ 原版物品标签不会自动收模组物品**，所以生成器同时往  
`data/minecraft/tags/items/` 写了 `swords` / `axes` / `pickaxes` / `shovels` / `trimmable_armor`  
五个标签把装备挂进去。不加的后果：绿宝石镐虽然能挖矿，但**不算 `ItemTags.PICKAXES`**，  
武灵修炼的持械判定（`WuLingType.HoldRequirement` 读的就是这几个标签）认不出来，  
玩家拿着它挖矿不给进度。

**盔甲层贴图**：护甲穿在身上时走 `ArmorMaterial#getName()` 的命名空间路径，  
所以材质名写成 `wulingdiguo:emerald`，两张贴图放  
`textures/models/armor/emerald_layer_1.png`（头盔 / 胸甲 / 靴子）与  
`emerald_layer_2.png`（**只有护腿**走这张）—— 原版 `HumanoidArmorLayer` 就是按「腿 / 非腿」分两张图。

**装备音效（2026-10-01）**：原版没有「绿宝石」装备音，`getEquipSound()` 返回  
`SoundEvents.ARMOR_EQUIP_NETHERITE`（原版最厚重的金属装备声）——  
此前沿用钻石音，用户反馈「绿宝石护甲的声音还是钻石护甲的声音」。

- 盔甲武灵**一次凝聚整套四件**（头盔 / 胸甲 / 护腿 / 靴子）——  
  2026-10-01 用户口径「护甲是全套护甲不是胸甲」；四件同名，靠 `wuling.manifest.armor_piece`  
  追加「· 头盔 / 胸甲 / 护腿 / 靴子」区分部位。其余境界同样给原版同材质的整套四件。  
  实现见 `WuLingType#manifestPiece`，`WuLingType#manifest` 因此返回 `List<ItemStack>`  
  （除护甲外恒为 1 件），凝聚时逐件生成实体。
- 创造物品栏也各放了一份裸件（战斗页放剑与胸甲，工具页放斧/镐/铲），**仅供试外观**；  
  实际强度要走「凝聚武灵」得到的那件（会再叠一次 `manifestAttackBonus`）。
- 原文第五部「一击 200+ 秒杀末影龙」尚未下发给具体数值，位置留在
  `ManifestItems` 里绿宝石剑的构造（现为 `ManifestItems#sword` 的工厂方法）。

### 分批缴纳（背包放不下）

后期突破要十几二十组物资，背包根本装不下，所以物资存在**两个去处**：

| 去处                                  | 说明                |
| ----------------------------------- | ----------------- |
| 背包                                  | 尚未缴纳的物资           |
| **缴纳池**（`WuLingData` 的 `Submit` 标签） | 已缴入的物资，可分批攒，与背包无关 |

- 面板按钮 **「提交物资」**（`WuLingSubmitPacket`）：把背包里**当前这档还缺的**物资尽量缴进池子  
  （只缴到需求上限，不多吞），背包腾空一块就能再缴一次，可以反复多次。
- 面板按钮 **「突破」**：**先自动把背包里剩余的也缴进池子**，再判定池子是否齐全。  
  所以一次性带齐时，点一次突破即可，不必先手动提交。
- 每一行显示 `已凑到 / 需要`，行名后追加灰色「已缴 N」，方便看清缴了多少。
- 缴纳池按**目标大境界**记账（`SubmitTarget`）；目标变了（已突破 / 改了配置）会  
  **自动原物退还**给玩家，不会凭空吞掉。`/wuling spirit unbind` 也会先退还再解绑。

### 物资需求配置

格式 `"物品注册名;数量"`，另有三个特殊键代表灵珠需求：

| 特殊键              | 含义                        |
| ---------------- | ------------------------- |
| `BEADS_TOTAL;N`  | **任意灵珠共 N 颗**，不限来源、不限品质（2026-10-02 起绿宝石档用这个） |
| `ALL_BEADS;N`    | **不限品质**，但要求每种怪物各 N 个 |
| `ALL_JI_BEADS;N` | 每种怪物各 N 个，只收**极品**灵珠（旧口径，代码保留兼容）    |


覆盖的怪物集合 = 注册表里全部 MONSTER 分类实体（模组怪物自动纳入）
∪ 本模组出图的怪物（疣猪兽是 CREATURE 分类却照样掉灵珠，靠出图表补进来）
− `Config.NEVER_DROPS`（蠹虫/恼鬼/末影螨/武灵僵尸）− `Config.EXCLUDED_MOBS` − `Config.BREAKTHROUGH_EXCLUDED_MOBS`。
`BREAKTHROUGH_EXCLUDED_MOBS` 默认排除 **巨人 / 疣猪兽 / 幻术师 / 远古守卫者 / 流浪者 / 监守者**
（它们照样掉灵珠，只是不参与这几档突破的收集要求）。

> **缴纳池的灵珠键带品质段**（`bead|<来源>|<品质>`）：不限品质时一次可能缴进多种品质，
> 分品质记账才能保证退还时「缴的是凡品就退凡品」，不会被白嫖成极品。
> 旧存档里没有品质段的键按极品处理。

| 过渡 | 默认需求 |
|---|---|
| 木 → 石 | 橡木原木 ×64（占位） |
| 石 → 黄金 | 圆石 ×512 + 煤 ×64（占位） |
| 黄金 → 玄铁 | 金锭 ×128 + 铁锭 ×256（占位） |
| 玄铁 → 钻石 | 铁块 ×128 + 黑曜石 ×256（占位） |
| 钻石 → 下界合金 | **金锭 ×1152 + 远古残骸 ×1152**（原文 18 组） |
| 下界合金 → 绿宝石 | **BEADS_TOTAL ×100 + 绿宝石块 ×10**（2026-10-02 口径：**任意灵珠 100 颗，不限来源与品质**） |

> 标「占位」的四段是你还没给的，数值是我随手填的，等你的正式数值。

#### ⚠️ 绿宝石档的键名换过两次

0.2.13 就把绿宝石档的默认值从 `ALL_JI_BEADS;10`（只收极品）改成了 `ALL_BEADS;10`（不限品质），
**但配置键名 `netherite_to_emerald` 没换** —— 而 Forge 的配置文件一旦生成就固定在那里，
代码改默认值对它无效。于是老存档里那份配置仍然是「只收极品」，
进游戏看到的还是「全体怪物极品灵珠」，看起来就像改动没生效。

0.2.23 把键名换成 **`emerald_beads_any_quality`**，新键会拿到新默认值 `ALL_BEADS;10`。

2026-10-02 又把要求从「每种怪物各 10 个」（27 种 × 10 = 270 颗）改成「任意灵珠 100 颗」
（`BEADS_TOTAL;100`），键名同步换成 **`emerald_beads_total`**。
判定逻辑上，`BEADS_TOTAL` 不走「每种怪物分别凑数」，而是把背包 + 缴纳池里的灵珠**不分来源直接累加**，
缴进池子时仍按「来源 + 品质」分键记账（`bead|<来源>|<品质>`），所以退还时一颗不串味。
`BREAKTHROUGH_EXCLUDED_MOBS` 对 `BEADS_TOTAL` 不起作用（任何来源的灵珠都算数）。

另外启动时会把六段突破的**生效值**打进日志（`Config#logEffectiveRequirements`），
以后遇到「改了却没生效」直接看日志即可，不用进游戏试。

## 五、怪物等级（武灵属性，0.2.21）

> 原文口径：「加入怪物等级系统（用木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石），
> 攻击都用本属性的剑做攻击；每种怪物都有小概率有属性，但怪物的等级越高越非常稀有！」

### 规则

| 项 | 口径 |
|---|---|
| 谁能有等级 | **敌对生物**（`Enemy`）且不在排除名单里；和平生物与村民不参与 |
| 等级阶梯 | 与玩家武灵**同一套 7 大境界**：木 → 石 → 黄金 → 玄铁 → 钻石 → 下界合金 → 绿宝石 |
| 有等级的概率 | `monsterTier.tierChance`，默认 **10%**（调 0 即关闭整个系统） |
| 等级分布 | 权重 = 1 ÷ `tierRarityRatio` ^ 阶数，默认 2.5 → 等级越高越非常稀有 |
| 武器 | **本属性的剑**：木剑 / 石剑 / 金剑 / 铁剑 / 钻石剑 / 下界合金剑 / **绿宝石剑**（本模组单独设计的那把） |
| 伤害 | 剑自带的属性修饰符由原版 `LivingEntity#handleEquipmentChanges` 自动挂上，不必自己写伤害逻辑 |
| 血量 | 倍率 = 1 + 大境界序号 × `tierHealthBonusPerRealm`（默认 0.5） |
| 掉落 | 主手物品掉落率钉成 **0**（否则刷出一柄绿宝石剑就等于绕开整条晋升线） |
| 提示 | 打死带等级的怪时，给击杀者报一句「击杀了一头 钻石阶 妖兽」 |

### 实际概率（默认 10% / 2.5）

| 等级 | 在「有等级的怪」里 | 占全部怪物 |
|---|---|---|
| 木 | 60.1% | 6.0% |
| 石 | 24.0% | 2.4% |
| 黄金 | 9.6% | 0.96% |
| 玄铁 | 3.8% | 0.38% |
| 钻石 | 1.5% | 0.15% |
| 下界合金 | 0.61% | 0.061% |
| 绿宝石 | 0.25% | **约 1/4000 只怪** |

### 排除名单（`monsterTier.tierExcludedMobs`）

- 不近战的：苦力怕、史莱姆、岩浆怪、恶魂、烈焰人、女巫、潜影贝；
- 不渲染手持物 / 另有攻击方式的：幻翼、守卫者、远古守卫者、蠹虫、末影螨、凋灵、末影龙。

理由：给它们剑既不会用也看不见，白掷一次骰子。删掉某项即可让它们参与。

### 几个取舍

- **武器即等级**：不做名字前缀、不加额外 UI。木阶一柄木剑、绿宝石阶一柄绿剑，
  一眼可辨，也顺便解释了「为什么这只僵尸打得这么疼」。
- **不设自定义名字**：给怪物 `setCustomName` 会牵扯「带名怪不消失」的判定，得不偿失。
- **血量走固定 UUID 的属性修饰符**，每次进世界先摘后挂，区块反复加载不会叠血；
  补血只在第一次应用时做，重载不会白送一次满血。
- **等级只掷一次**：结果写进怪物的 Forge 持久化数据（`ForgeData`），区块卸载再加载不会重掷。
- **隐性联动**：灵珠品质本来就按「来源怪最大生命值」推算（`CorpseEntity#randomQuality`），
  所以高阶怪掉的灵珠品质天然更好。

代码入口：`ModEvents#onEntityJoinLevel` → `MonsterTier#onJoin`（`wuling/MonsterTier.java`）。

## 九、Forge 版本兼容性（0.2.24）

### 结论

产物可加载到 **Minecraft 1.20.1 的全部 132 个 Forge 版本**上：`47.0.0` ~ `47.4.23`
（官方推荐版是 47.4.10，最新版 47.4.23）。

`mods.toml` 里声明的范围：

| 项 | 值 | 含义 |
|---|---|---|
| `loaderVersion` | `[47,)` | 47.x 全部 |
| forge 依赖 `versionRange` | `[47,)` | 同上 |
| minecraft 依赖 `versionRange` | `[1.20.1,1.21)` | 1.20.1 |

### 做法：编译目标锁在「最低」版本

`gradle.properties` 的 `forge_version` 故意设成 **47.0.0**（不是最新的 47.4.23）。

用最低版本编译，产物字节码里就**只会引用 47.0.0 时已经存在的 API**，
于是天然能跑在更高的版本上；反过来编译最新版则很容易悄悄用上后期新增的 API，
在老版本上直接崩。代价是开发时 `runClient` 跑的是 47.0.0。

> 想在**新版** Forge 上调试：把 `gradle.properties` 的 `forge_version` 改回 `47.4.23`，
> 或者临时用 `gradle runClient -Pforge_version=47.4.23`（命令行属性优先，不用改文件）。

### 踩到的三个坑

**① 主类构造函数必须是无参的**（影响最大）

- `47.0.0 ~ 47.3.7` 的 `FMLModContainer#constructMod()` 只有一句
  `modClass.getDeclaredConstructor().newInstance()` —— **只认无参构造函数**，
  找不到就 `ModLoadingException` 加载失败。
- `47.3.10` 起才支持把 `FMLJavaModLoadingContext` 注入构造函数
  （实现是「先试带参、`NoSuchMethodException` 再退回无参」）。
- 所以**写无参构造函数在新老版本都能被实例化**，是最安全的写法。
  本项目原来用的是 `public WulingEmpire(FMLJavaModLoadingContext context)`，
  在 **132 个版本里的 89 个**（47.0.x 23 个 + 47.1.x 38 个 + 47.2.x 20 个 + 47.3.0~47.3.7 8 个）上会加载失败。

**② 配置注册用 `ModLoadingContext`**

`FMLJavaModLoadingContext#registerConfig` 不能直接用：47.0.0 里
`FMLJavaModLoadingContext` 是个**独立类**（不继承 `ModLoadingContext`），根本没有这个方法；
继承关系是后期才加的。改用从 1.20.1 初版就存在的
`ModLoadingContext.get().registerConfig(ModConfig.Type.COMMON, Config.SPEC)` 即可。

**③ `ResourceLocation` 的静态工厂是后期 backport 进来的**

`fromNamespaceAndPath` / `parse` / `withDefaultNamespace` / `bySeparator` / `tryBySeparator`
这一批**是 Forge 在 1.20.1 后期补进 MC 的**，47.0.0 里没有。
统一改用两参构造函数 `new ResourceLocation(namespace, path)` —— 它从 1.20.1 初版就在，
在最新版也照样可用（只是有 deprecation 提示）。

原来项目里有 4 处用了 `fromNamespaceAndPath`：

| 文件 | 位置 |
|---|---|
| `WulingEmpire` | `id(String)` |
| `capability/ModCapabilities` | `SPIRIT_POWER_ID` / `WU_LING_ID` 两个**静态字段** |
| `item/SpiritQuality` | `itemTexture()` |
| `wuling/WuLingType` | `id()` |

其中 `ModCapabilities` 那两个是**静态字段初始化**——在旧版 Forge 上会在类加载时
直接抛 `NoSuchMethodError`，属于「一进游戏就崩」，不是偶发问题。

> `ResourceLocation.tryParse(String)` 两版都有，**不需要改**。

### 怎么验证的

1. **编译即清单**：直接把 `forge_version` 降到 `47.0.0` 编译——编译器会逐条报出
   所有在老版本不存在的 API（上面第 ③ 条的 4 处就是这么被抓出来的）。
2. **运行时冒烟**：在两端各起一次专用服务器，都跑到 `Done (...)! For help, type "help"`：
   - Forge **47.0.0**（最低版）→ `《武灵帝国》初始化完成，MODID = wulingdiguo` + `Done (10.442s)`
   - Forge **47.4.23**（最新版）→ 同样通过
3. **产物复查**：`javap` 确认 `WulingEmpire` 只剩 `public WulingEmpire();`，
   构造函数字节码里是 `FMLJavaModLoadingContext.get()` + `ModLoadingContext.registerConfig`；
   jar 内所有 class 里搜不到 `fromNamespaceAndPath` 等字样。

### 版本边界速查

| Forge 版本段 | 数量 | 无参构造函数 | 注入构造函数 |
|---|---|---|---|
| 47.0.0 ~ 47.0.50 | 23 | ✅ 必须 | ❌ 不可用 |
| 47.1.0 ~ 47.1.47 | 38 | ✅ 必须 | ❌ 不可用 |
| 47.2.0 ~ 47.2.36 | 20 | ✅ 必须 | ❌ 不可用 |
| 47.3.0 ~ 47.3.7 | 8 | ✅ 必须 | ❌ 不可用 |
| 47.3.10 ~ 47.3.39 | 22 | ✅ 可用 | ✅ 可用 |
| 47.4.0 ~ 47.4.23 | 21 | ✅ 可用 | ✅ 可用 |

**总 132 个版本，全部支持。**


## 十、产物命名（0.2.27）

构建产物统一命名：

```
Wuling-Empire-v<mod_version>.jar
    └─ 例：Wuling-Empire-v0.2.27.jar
```

实现（`build.gradle`）：

```groovy
version = "v${mod_version}"     // → v0.2.27
base {
    archivesName = 'Wuling-Empire'
}
```

- 只用 `archivesName` + `version` 两处，`jar` / `reobfJar` / `sourcesJar`
  都从 `base` 派生，因此**不会产生两份名字不同的产物**。
- `version` 带 `v` 前缀只影响文件名；`mods.toml` 里的 `version="${mod_version}"`
  取自 `gradle.properties`，仍是干净的 `0.2.27`。
- Manifest 的 `Implementation-Version` 也显式写回 `mod_version`（不带 `v`），
  防止解析 Manifest 的工具把 `v0.2.27` 当非法版本号。
- **与文件命名无关、不要动的东西**：`mod_id=wulingdiguo`（存档、注册表 ID、
  配置目录 `config/wulingdiguo-common.toml` 都靠它）、`displayName`（游戏 Mod 列表显示）。

> 历史：≤ 0.2.26 的产物名为 `wulingdiguo-0.2.x.jar`（当时 `archivesName = mod_id`）。

### 附一：Mod 名称的中文乱码（0.2.27 修复）

**症状**：游戏 Mod 列表里显示成 `WuLing Diguo / æ¦çµå¸å½`、简介也是一串西欧字母。
**存在时间**：至少 0.2.20 ~ 0.2.26 的产物全部中招（不是新引入的问题）。

**排查链**（三步，值得记下来）：

1. **看 jar 里的字节**，不要看构建日志：
   `META-INF/mods.toml` 的 `displayName` 是
   `c3 a6 c2 ad c2 a6 …` —— 这是「UTF-8 的中文被按 latin-1 解码后再编成 UTF-8」的
   典型**双重编码**指纹（正常应是 `e6 ad a6 e7 81 b5 …`）。
2. **确认读的一方没问题**：Forge 1.20.1 用 NightConfig 读 mods.toml。
   反编译 `com/electronwill/nightconfig/core/file/GenericBuilder.class` 可见
   `getstatic StandardCharsets.UTF_8` → **默认就是 UTF-8**，不必怀疑 Forge。
3. **问题在写的一方**：Gradle 按 **ISO-8859-1** 读取 `gradle.properties`
   （沿用 `java.util.Properties` 规范），所以 `mod_name=武灵帝国` 一进 Gradle 就已
   变成 `æ¦çµå¸å½`；再经 `processResources` 的 expand 以 UTF-8 写盘 → 双重编码。

**改法（两处）**：

| 位置 | 改动 |
|---|---|
| `gradle.properties` | `mod_name` / `mod_description` 的非 ASCII 全部写成 `\uXXXX` 转义 |
| `build.gradle` | `tasks.named('processResources') { filteringCharset = 'UTF-8' }` |

第二处是**必要的加固**：不显式指定时，expand 的写盘字符集取「构建机默认字符集」，
在中文 Windows（GBK）上构建会把中文写成 GBK 字节，依旧乱码 —— 也就是说，
原来的构建能侥幸不出第二种错，只是因为构建命令带了 `-Dfile.encoding=UTF-8`。

**规则**：`gradle.properties` 视为**纯 ASCII 文件**。要在里面写非 ASCII 值？
先转义。文件顶部已加了醒目注释。

**验收**：解包 jar，`mods.toml` 里 `武灵帝国` 必须是 `e6 ad a6 e7 81 b5 e5 b8 9d e5 9b bd`。

### 附二：另两处「名字」

- `settings.gradle` 加了 `rootProject.name = 'Wuling-Empire'`：
  Manifest 的 `Implementation-Title` 取自它，不写就取文件夹名（改文件夹名＝改产物元数据）。
- Manifest 的 `Implementation-Version` 显式写 `mod_version`（`0.2.27`），
  不跟着文件名一起带 `v` 前缀，方便校验工具解析。

### 发布工具 `tools/publish_github.py`

WorkBuddy 沙箱注入了本地 HTTP 代理，`git push` 会被拒绝
（`CONNECT tunnel failed, response 502`），绕开代理直连又被沙箱屏蔽，
因此本项目**改用 GitHub REST API 同步**（`api.github.com` 与 `uploads.github.com` 均放行）。

```bash
python tools/publish_github.py status            # 列出本地与远程的差异
python tools/publish_github.py sync              # 提交并推送到 main
python tools/publish_github.py sync -m "说明"    # 自定义提交信息
python tools/publish_github.py release 0.2.29    # 建 tag + Release + 上传 jar
python tools/publish_github.py sync --release    # 同步源码后再发布
```

实现要点：

- **差异用 blob sha 对撞**：远程 `git/trees?recursive=1` 的 sha 对本地
  `git hash-object -w --path=<p> <p>`。`--path` 让 `core.autocrlf` 与 `.gitattributes` 生效，
  所以算出的 sha 与 GitHub 完全可比 —— **既精确又不会出现 CRLF 假差异**。
- **上传内容从 `git cat-file blob` 取**，与 sha 严格对应；提交后还会校验远程返回的 sha 是否一致。
- **文件枚举交给 git**（`ls-files -s` + `ls-files --others --exclude-standard`），
  所以 `.gitignore` 天然生效，无需自己实现忽略逻辑。
- **二进制安全**：blob 以 base64 提交，jar / png 不会被破坏
  （MCP 的 `push_files` 是纯文本接口，传二进制会静默损坏，不可用于此场景）。

```groovy
base { archivesName = 'Wuling-Empire' }
```

`mod_suffix` 定义在 `gradle.properties`（默认留空）。三种写法都行：

| 方式 | 例子 | 适用 |
|---|---|---|
| 改文件 | `mod_suffix=test` | 整段时间都发测试版 |
| 命令行 | `gradle build -Pmod_suffix=test` | 只这一次，不动文件 |
| 留空 | `mod_suffix=` | 正式版 |

后缀词任意，只要**纯 ASCII、不带空格和点**（`test` / `pre1` / `rc1` / `dev` 都可以）。
不要写成 `0.3.0-test.1` 之类带点的值，语义化版本比较会出问题。

### 后缀「只」影响文件名

| 字段 | 是否受影响 |
|---|---|
| jar 文件名 | ✅ 加后缀 |
| Manifest `Implementation-Version` | ✅ 加后缀（`0.3.0-test`），便于区分两类产物 |
| `mods.toml` 的 `version` | ❌ 仍是 `${mod_version}` = `0.3.0`（Forge 靠它判版本，必须干净） |
| `mod_id` / `displayName` | ❌ 不动 |

> 为什么 `mods.toml` 的 version 不带后缀：Forge 用语义化版本比较 mod 依赖关系，
> 而 `-test` 是 semver 的**预发布标识**，会让「0.3.0-test < 0.3.0」成立 ——
> 万一写成依赖坐标，正式版反而被判为更新。文件名带后缀足够区分了。

### 发布

```bash
# 正式版
python tools/publish_github.py release 0.3.0
#   产物 build/libs/Wuling-Empire-v0.3.0.jar  → tag v0.3.0

# 测试版
python tools/publish_github.py release 0.3.1-test
#   产物 build/libs/Wuling-Empire-v0.3.1-test.jar → tag v0.3.1-test
```

`publish_github.py` 的产物路径就是按 `Wuling-Empire-<tag>.jar` 拼的，
所以**带后缀直接跟着 tag 走**，无需额外参数。要用别的文件名（比如改名过的 jar）
再加 `--jar <路径>`。

| `gradle build` | `Wuling-Empire-v0.3.0.jar`（178,800 B） | `0.3.0` |

两次 `BUILD SUCCESSFUL`；`mods.toml` 的 `displayName="WuLing Empire / 武灵帝国"`、

### 上传资产的 502 重试（0.3.0 加固）

发布 v0.3.0 时 `uploads.github.com` 连续 3 次报
`Tunnel connection failed: 502 Bad Gateway`，而 `api.github.com` 全程正常 ——
沙箱代理对该主机的拦截是**间歇性**的（同一时刻 `uploads.github.com/user` 能通、根路径不通）。

`publish_github.py` 因此做了两层加固：

| 层 | 做法 |
|---|---|
| 通用请求重试 `api()` | 网络层异常 / HTTP 5xx / 429 自动重试，最多 4 次，退避 2s / 4s / 6s；4xx（除 429）是确定性错误，立即返回 |
| 资产上传重试 `upload_asset()` | **只在 `uploads.github.com` 上重试**，最多 8 次，每次间隔 3s |

> ⚠️ **0.3.1 修正 —— 0.3.0 的「双通道」是错的，别照抄**：
> 资产上传**只能**用 `uploads.github.com` 作为 host。写成
> `POST https://api.github.com/repos/{owner}/{repo}/releases/{id}/assets?name=...`
> 会返回 **404** —— 那个路径在 api 主机上只支持 GET（列出资产），不支持上传。
> 0.3.1 发版时实测踩到了这个 404。正确做法是**在同一主机上多试几次**，不做 host 回退。

补充观测：两个主机解析到不同 IP（`uploads.github.com` → `20.205.243.161`、
`api.github.com` → `20.205.243.168`），代理对两个后端的放行策略可能不一致，
所以**不要把「上传成功」当必然**，脚本的自动重试是必需的。

## 十五、武灵实物独立注册 · 随境界升级 · 满灵力吸珠（2026-10-01）

### 口径

用户三条要求：
1. **灵力满时吸收灵珠 = 小幅度增加修为**（不再直接拒绝吸收）；
2. **每一级升级时手上的武灵物品一同升级**；
3. **武灵物品重新注册为新物品**（追问确认：每个境界都要独立的物品 ID）。

### 一、91 件独立物品（`item/ManifestItems`）

取代 0.2.x 的「拿原版木剑改个名字」：现在是 **每种境界 × 每种武灵 = 一件真正注册的物品**。

| 维度 | 取值 | 数量 |
|---|---|---|
| 境界 | 木 / 石 / 黄金 / 玄铁 / 钻石 / 下界合金 / 绿宝石 | 7 |
| 单件类 | 剑 / 斧 / 镐 / 铲 / 弓 / 水 / 火 / 红石 / 书 | 9 |
| 护甲 | 头盔 / 胸甲 / 护腿 / 靴子 | 4 |
| 合计 | 7 × (9 + 4) | **91 件** |

- **id 规则** `<境界key>_<种类或部位key>`：`wulingdiguo:wood_sword`、
  `wulingdiguo:meteor_iron_pickaxe`、`wulingdiguo:emerald_boots`。
  绿宝石档沿用 0.2.x 的 id（`emerald_sword` 等），只是从 `ModItems` 搬到了 `ManifestItems`。
- **材质对应**：工具 = 木 wooden / 石 stone / 黄金 golden / 玄铁 iron / 钻石 diamond / 下界合金 netherite；
  护甲 = 皮革 / 锁链(`ArmorMaterials.CHAIN`) / 黄金 / 铁 / 钻石 / 下界合金。
  绿宝石档走 `ModTiers.EMERALD` / `ModArmorMaterials.EMERALD`（数倍于钻石）。
- **低境界不重复做贴图**：模型直接以原版同名物品模型为 parent
  （`{"parent":"minecraft:item/wooden_sword"}`），由 `tools/gen_manifest_models.py`
  生成 83 份；绿宝石档 8 件的染色贴图 + 模型仍归 `tools/gen_emerald_gear.py`。
- **物品名不写 lang 表**：`ManifestItems` 内部覆盖 `Item#getName(ItemStack)` 现算
  （`wuling.manifest.name` + 护甲部位后缀 `wuling.manifest.armor_piece`），
  省掉 91 × 2 条语言键，也避免名字带原版「自定义名」的斜体。
- 主类里 `ManifestItems.ITEMS.register(modBus)` 与 `ModItems.ITEMS` 并列注册。

### 二、凝聚物标记 → 随境界升级

- 凝聚时给物品写 NBT 标记 `WuLingManifest = <武灵种类 key>`（`ManifestItems#markManifest`）。
- **大境界突破**成功后（`WuLingBreakthroughPacket#perform`）调用
  `WuLingBinding#refreshManifestItems(player)`：扫背包（含护甲槽、副手，共 41 格）里
  带标记的物品，全部换成**当前境界**的同款，并提示「已更新 N 件」。
- 已经是对应那件的会跳过，所以**小境界晋升**时（`ModEvents#cultivate` 里也调了一次）
  不会改任何东西 —— 语义上「每一级升级都会同步」，但没有白刷耐久的副作用。
- 玩家自己做 / 捡的原版装备不带标记，**不会被换掉**。
- `WuLingType#manifest` 因此从「返回单件」改成返回 `List<ItemStack>`（护甲整套四件），
  并新增 `manifestPiece(realmOrdinal, stageOrdinal, armorPart)` 供升级替换单件时使用。

### 三、满灵力吸珠换修为

- 配置 `spirit.beadFullProgress`（默认 `3.0`，`0` = 关闭 → 回到旧行为）。
- 灵力已满时吸收：**不涨灵力**，改为累积修为，
  实际累加 = `beadFullProgress × 该灵珠品质的吸珠倍率`（见下）。
- **吸珠倍率**（`spirit.beadAbsorbBonus*`，2026-10-11 用户口径「吸收极品灵珠时给的修为可以多一点」）：
  凡 `1` / 良 `1.5` / 优 `2` / 上 `3.5` / **极 `6`** —— 比修炼速度倍率更陡，
  默认值下换算成进度就是 `3 / 4.5 / 6 / 10.5 / 18`。
- ⚠️ 这条路径**不叠乘修炼速度倍率**（`cultivationBonus*`）：走 `WuLingData#addProgressRaw`
  而不是 `addProgress`。喂修为看的是**珠子**多稀有，与玩家自己用什么品质开启的武灵无关；
  两条曲线相乘会把极品珠顶到 18 倍。
- 直接走 `WuLingData`，**不经过** `IWuLing#addProgress` 的「动作匹配」判定 ——
  吸珠对任何武灵种类都算数（否则剑武灵就换不到修为）。
- 没开启武灵的玩家吸满灵力的珠子仍被拒绝（免得白费珠子）。
- 触发小境界晋升时同样发 `stage_up` 提示并同步物品。
- tooltip 有 `tooltip.wulingdiguo.bead_full_progress` 一行，把这颗珠子能换多少修为直接写出来，
  否则玩家看不出极品珠为什么值钱。

### 四、其它联动

- `MonsterTier#swordOf` 改为查 `ManifestItems`（怪物手里的「本属性剑」现在也是对应境界那件）。
- 创造物品栏战斗页：绿宝石剑 + 整套四件护甲；工具页：绿宝石斧 / 镐 / 铲。

## 十六、腐肉武灵：召唤类（2026-10-02）

用户口径：「加入新武灵腐肉：稀有 1/100000，随着攻击僵尸修为提升，
升级不消耗材料，只消耗击杀僵尸的量，每有一个小境界可凝聚 5 只僵尸，
自动攻击敌对生物。在钻石境界时，僵尸可以飞行。」

> 本轮问答澄清的四处歧义：
> - 数量「按**大境界**算」（木 5 → 绿宝石 35），不是按 21 个小台阶；
> - 僵尸**跟随玩家**，用 **Shift + P 手动消散**（不是限时消失）；
> - 「击杀僵尸」统计**僵尸类全家**（僵尸 / 小僵尸 / 尸壳 / 溺尸 / 僵尸村民 / 僵尸猪灵）；
> - 稀有度**真的做成超稀有**（约百万分之一），不只是写个标签。

### 一、它和其它武灵的本质差别

普通武灵是「物品型」：凝聚 → 掉一件实物 → 实物带境界属性。
腐肉是**召唤型**：

| | 物品型武灵 | 腐肉 |
|---|---|---|
| 凝聚产物 | `ManifestItems` 里的实物 | 一队 `wu_ling_zombie` 实体 |
| 修炼动作 | 伤害 / 挖掘 / 射箭 / 承伤 / 用道具 | **只认攻击僵尸类** |
| 突破货币 | 物资（背包 + 缴纳池） | **累计击杀僵尸数** |
| 随境界升级 | 背包里的实物换新 | 无实物可换（只影响召唤数量 / 飞行） |

凡是「按武灵种类分叉」的地方都多一条 summoner 分支，统一入口是
`WuLingType#isSummoner()`，不要在别处写 `== ROTTEN_FLESH` ——
将来再加召唤类武灵时只改这一个判定。

### 二、稀有度：配平出来的权重，不是概率

抽取是权重制（`WuLingType#roll`）。要让腐肉落在 1/100000：

```
其余 10 类权重之和 = 5×1 + 5×10 = 55
w / (55 + w) = 1e-5  →  w ≈ 55 × 1e-5 = 0.00055
```

配置键 `rottenFlesh.mythicWeight`（默认 0.00055）。
**这不是「1/100000」的字面数** —— 直接填 0.00001 会得到约 1/550 万，
比设定稀有 55 倍。将来调整基类权重，这个值要跟着重算。

### 三、召唤数量与飞行

```
数量 = (大境界序号 + 1) × zombiesPerRealm      // 默认 5
  木 5 · 石 10 · 黄金 15 · 玄铁 20 · 钻石 25 · 下界合金 30 · 绿宝石 35
```

判定入口 `RottenFleshRule#summonsFor`。飞行则是
`realmOrdinal >= flyFromRealm`（默认 4 = 钻石），见 `RottenFleshRule#canFly`。

### 四、突破：只认击杀数

`Config#zombieKillsFor(n) = killBase × killGrowth^(n-1)`，默认
**20 / 50 / 125 / 312 / 781 / 1953** 只。

- 计数存在 `WuLingData#zombieKills`（NBT `ZombieKills`），**只增不减**，
  突破时按档扣除（`consumeZombieKills`）。
- 只统计「玩家亲手击杀」的僵尸类（`ModEvents#onZombieSlain`）——
  别的生物互殴致死、或僵尸白天自燃死掉的都不算。
- **自家召唤的随从不算**（0.3.5）：`WuLingZombieEntity` 继承原版 `Zombie`，
  不排掉的话「召唤一批 → 自己打死」能白刷击杀数；同理它也不掉灵珠
  （`Config.NEVER_DROPS` 加了 `wulingdiguo:wu_ling_zombie`）。
- 解绑 / 换武灵会把计数清零（等于重头再来）。
- `WuLingBreakthroughPacket` 按 `isSummoner()` 分叉：走击杀数判定，
  **完全不碰缴纳池**，也不会误退物资。

### 五、召唤僵尸实体（`entity/WuLingZombieEntity`）

继承原版 `Zombie` —— 白拿模型 / 贴图 / 动画 / 音效，渲染器直接复用
`ZombieRenderer`，我们只改行为：认主、只打敌对生物、跟随、不烧身、
不因距离被回收、不掉战利品不给经验、按境界可飞行。

⚠️ 四个容易踩的点（都是实打实会出问题的）：

1. **父类那套目标选择器必须整体丢掉** —— `registerGoals` 里**不要**调 `super`。
   Zombie 默认会打玩家和村民，留着就是「召唤物反过来咬主人」。
2. **父类还会在别处 `setTarget`**（被攻击时、拉援军时），绕过目标选择器，
   所以额外覆写 `setTarget` 再拦一道。只改 `registerGoals` 是不够的。
3. **实体分类用 `MobCategory.MISC`** 而不是 `MONSTER`：MONSTER 会挤占刷怪
   上限（70），一波召唤 35 只就会把自然刷怪掐死，玩家会以为「召唤把刷怪搞没了」。
4. **飞行状态要走 `SynchedEntityData`**，只写服务端 NBT 的话客户端会
   一边悬停一边往下飘（两边 `travel` 各算一次）。

### 六、Shift + P 解散

`network/WuLingDismissPacket`（通道号 7）→ 服务端按 `ownerUUID` 找出该玩家
名下**全部**召唤僵尸并 `discard()`。只删自己的，别人的队伍动不了。

按键注册在 `ModKeyMappings.DISMISS`（P 键）；Shift 仍在 `ClientTickHandler`
里单独判断 —— 1.20.1 的 `KeyMapping` 不支持修饰键。

### 七、配置文件

| 键 | 默认 | 说明 |
|---|---|---|
| `rottenFlesh.mythicWeight` | 0.00055 | 传说档抽取权重（≈ 1/100000） |
| `rottenFlesh.zombiesPerRealm` | 5 | 每个大境界召唤只数 |
| `rottenFlesh.killProgress` | 8.0 | 击杀一只僵尸的修为进度 |
| `rottenFlesh.killBase` | 20 | 第一档突破所需击杀数 |
| `rottenFlesh.killGrowth` | 2.5 | 每档击杀数增长倍率 |
| `rottenFlesh.flyFromRealm` | 4 | 从哪个大境界起能飞（4 = 钻石） |

# 第十七章 红石装备（充能类，0.3.6）

| 镐 | `III` / ` S ` / ` S ` | 3 |
| 铲 | `I` / `S` / `S` | 1 |

`I` = 红石锭，`S` = 木棍。一整套 = **24 锭 = 216 颗红石粉**（用户明确选择红石粉保持 1 个/次，
不考虑一次多产）。红石粉 → 锭必须用 tag，因为七件粉是七个不同物品。

## 二、强度：境界 + 1 档，封顶绿宝石

| 玩家境界 | 红石装备档位 | 剑（示例） |
| --- | --- | --- |
| 木 | 石档 | 20 |
| 石 | 黄金档 | 32 |
| 黄金 | 玄铁档 | 54 |
| 玄铁 | 钻石档 | 77 |
| 钻石 | 下界合金档 | 112 |
| 下界合金 / 绿宝石 | **绿宝石档（封顶）** | 240 |

**目标数值的实现**：不去抄一遍「原版同款 × 境界倍数」，而是直接
**构造那一档的武灵凝聚物**（`WuLingType#manifestPiece`）读它的属性总和 ——
「+1 档」拿到的就严格是「那个档的武灵装备」的数值，永远不会与凝聚物产生偏差。
结果按「档位 × 件数」缓存（最多 7 × 8 组）。

**为什么基础材质给得很低**（`ModTiers#REDSTONE` / `ModArmorMaterials#REDSTONE` 只有石 / 锁链水平）：
充能耗尽时加成必须能**整体撤掉**，而材质自带的属性（`Item#getDefaultAttributeModifiers`）
是无法移除的，NBT 上的修饰符才可以。所以基础给弱材质、强度全靠可增可减的修饰符托着。

> 例外：**挖掘速度**在 1.20.1 只能由 `Tier#getSpeed` 决定（它不是属性修饰符），
> 没法动态改，所以直接给铁档水平的 10 点，不随境界变化。

## 三、充能池：整套共享

存在玩家数据里（`WuLingData#redstoneCharge`，NBT `RedstoneCharge`），**不是**记在某件装备上 ——
用户口径是「护具或武器自带的所有武器灵力共享」，共享池记在单件物品上没法共享。
默认上限 `redstone.maxCharge = 1000`。

**充能换算**直接复用灵珠的回复量口径（`BeadPower`）：

```
充能点 = 该灵珠的回复量（% = 怪物基准 × 品质倍率）× redstone.chargePerPercent（默认 10）
```

所以僵尸凡品珠 = 5% → **50 点**，末影龙极品珠 = 100% → **1000 点**（刚好充满）。
两种资源（玩家灵力 / 装备充能）共用同一个强度标尺，不必另造表，也不会出现
「某种怪物的珠子对装备特别划算」的失衡。

> 与武灵无关：未开启武灵的玩家照样能穿能充，`WuLingData#unbind()` **不清**这个值
> （不像击杀数那样跟着武灵走）。

## 四、耗能点

| 行为 | 配置 | 默认 | 判据 |
| --- | --- | --- | --- |
| 攻击命中 | `costAttack` | 10 | `LivingHurtEvent` 里攻击者是玩家且手持红石武器 |
| 挖掘方块 | `costMine` | 5 | `BlockEvent.BreakEvent` 里玩家手持红石工具 |
| 挨打受击 | `costHurt` | 10 | `LivingHurtEvent` 里受击者是玩家且穿着红石护甲 |
| 飞行 | `costFly` | 20 / 秒 | 穿红石靴子 + 在飞 + `tickCount % 20 == 0` |

## 五、耗尽的后果（全部走属性修饰符，不用药水效果）

| 后果 | 实现 |
| --- | --- |
| 装备加成失效 | 把装备上我们挂的修饰符撤掉（`RedstoneGear#refresh` 传 `powered=false`） |
| 不能飞 | 收回 `Abilities#mayfly` 并同步 `onUpdateAbilities()`（创造 / 旁观玩家不动） |
| 攻击大幅下降 | 玩家身上 `ATTACK_DAMAGE` 的 `MULTIPLY_TOTAL` 惩罚（`emptyAttackPenalty` 0.6 = 只剩 40%） |
| 速度减缓 | 玩家身上 `MOVEMENT_SPEED` 的 `MULTIPLY_TOTAL` 惩罚（`emptySpeedPenalty` 0.3 = 只剩 70%） |

后两条用的是 `addTransientModifier`（只存在内存、不写进玩家 NBT），
充上能或脱下红石装备就立刻撤掉。

## 六、飞行

穿红石靴子 + 充能 > 0 → `mayfly = true`，像创造那样飞；起飞后每秒扣 `costFly`。
充能耗尽或脱下靴子 → 立刻收回飞行（正在飞的话同时清掉 `flying`，不会浮在半空）。

## 七、充能菜单

**入口**：手持任意红石装备**右键**（`PlayerInteractEvent.RightClickItem`，服务端判定后发
`RedstoneOpenPacket` 让客户端开界面）。

界面 `client/RedstoneChargeScreen`：列出背包里的灵珠，按「来源 + 品质」聚合成一行
（品质色块 + 名字 + 数量 + 每次充能量），点「充能」消耗一颗。
界面**不缓存**背包快照，每帧直接读背包重建 —— 服务端扣完珠子界面立刻跟着变。

服务端 `RedstoneCharging#chargeFromBead` 只按「来源 + 品质」找第一颗符合条件的珠子消耗，
客户端传的是意图不是结果（即使客户端与背包不同步也不会扣错东西）。

# 第十八章 建筑系统（悬空坠落，0.4.0）

> 用户口径（2026-10-02）：
> 「新增建筑系统：每种方块玩家放置时若底下没有方块则像沙子一样向下坠落（延迟2秒），
> 在延迟时需要向方块上右键使用粘液球这样才不会坠落（自然产生的地形或建筑除外）」
>
> 追问后确定：粘液球**只固定点中的那一格**；**没固定**的方块在支撑被抽掉后仍然要掉
> （像真沙子一样持续判定）；**固定过的**则从此永久豁免，支撑被抽掉也不掉
> （2026-10-11 用户报「固定后挖掉底下还是会掉」，补明确）；火把 / 门 / 花 / 告示牌 / 铁轨
> 这类**依附型方块豁免**。

## 一、规则

| | |
| --- | --- |
| 触发 | 玩家放下方块，且**正下方没有支撑** |
| 延迟 | `building.delayTicks`（默认 40 tick = 2 秒） |
| 干预 | 倒计时内**手持粘液球右键那一格** → **永久固定**，之后永远不掉（默认消耗 1 颗） |
| 持续判定 | 方块下方的方块被挖 / 被炸时，上方那一串重新进入 2 秒倒计时；**碰到固定过的方块就停** |
| 例外 | 自然生成的地形与建筑；依附型小方块；带方块实体的方块 |

## 二、怎么区分「玩家放的」和「自然生成的」

原版方块没有通用 NBT，没法在方块自己身上做记号，所以另存一份台账：
`building/BuildingSavedData`，落在 `<存档>/data/wuling_building.dat`，每个维度一份，
内容就是「玩家放置过的方块位置」的 long 数组（`BlockPos.asLong()` 打包，`LongSet` 存）。

自然生成的方块从来没进过台账，所以压根不会被受理 —— 不需要去猜事件来源。

台账必须**持久化**：持续判定意味着方块放好、2 秒也过了之后还要能被追责，
服务器重启后台账一丢，这条规则就断了。

## 三、为什么不能只检查「放置那一刻」

用户选了持续判定。于是有三个入口都会排队：

| 入口 | 事件 | 做什么 |
| --- | --- | --- |
| 放置 | `BlockEvent.EntityPlaceEvent` | 登记台账；底下没支撑就排进队列 |
| 挖掘 | `BlockEvent.BreakEvent` | 台账划掉自己，**让上方那串重新排队** |
| 爆炸 | `ExplosionEvent.Detonate` | 同上，逐个处理被炸掉的方块 |

「上方那串」指从被移除方块的**正上方**开始，连续向上、且都在台账里的方块
（`BuildingSystem#scheduleChainUp`），遇到空气 / 非玩家放置 / 依附型方块 / **固定过的方块**就停。
它们拿同一个到期时刻，所以整根柱子会一起落，而不是从上往下一格一格地掉。

**固定是状态，不是「取消这一次倒计时」**：`BuildingSystem#pin` 除了把方块从队列里摘掉，
还会往台账里写一条固定记录（`BuildingSavedData#pin`，落盘，跨重启有效）。
不这么做的话，玩家固定完、再挖掉底下那格，持续判定一跑又把它排进队列，就等于白固定了。
固定记录在方块消失（挖 / 炸 / 坠落后）和「同一位置重新放置」时一并作废。

## 四、坠落怎么实现

直接交给原版 `FallingBlockEntity.fall(level, pos, state)` —— 沙子用的那套，不自己写下落物理。
它在落地时会把方块放回原位。

**代价**：带方块实体的方块（箱子、熔炉、潜影盒…）不参与坠落，
因为「转实体 → 落地」这一趟不带 `BlockEntity` 数据，会把里面的东西丢掉。
判定上直接 `state.hasBlockEntity()` 排除。

## 五、哪些方块不参与

`BuildingSystem#qualifies` 逐条排除：

| 排除项 | 判据 | 原因 |
| --- | --- | --- |
| 空气 | `state.isAir()` | — |
| 带方块实体 | `state.hasBlockEntity()` | 下落会丢内容 |
| 依附型小方块 | `BuildingSystem#isAttached` | 见下 |
| 无碰撞箱 | `getCollisionShape().isEmpty()` | 火把、花、草、红石线 |
| 硬名单 | `Config.BUILDING_NEVER_FALLS` | 基岩、屏障、结构方块、指令方块… |
| 玩家配置 | `building.excludedBlocks` | 兜底 |

依附型（`isAttached`）走方块标签判定：`DOORS` / `TRAPDOORS` / `FENCE_GATES` / `BEDS` /
`BANNERS` / `ALL_SIGNS` / `CLIMBABLE` / `RAILS` / `PRESSURE_PLATES` / `BUTTONS` /
`CANDLES` / `FLOWER_POTS` / `CROPS` / `SAPLINGS` / `FLOWERS` / `LEAVES` / `WOOL_CARPETS` / `FIRE`，
外加 `LanternBlock` / `ChainBlock` / `DiodeBlock`（中继器、比较器）/ `SnowLayerBlock` / `LadderBlock`。
不豁免的话，贴墙的告示牌、地上的压力板、门、铁轨会在放下 2 秒后掉一地。

## 六、「有没有支撑」的判据

`BuildingSystem#isFree`，与原生沙子同一套（`FallingBlock#isFree`）：
空气、火、流体、以及「可被替换」的东西算没有支撑；台阶、栅栏这类有实体碰撞箱的算有支撑。

## 七、状态放哪

| 状态 | 位置 | 是否持久化 |
| --- | --- | --- |
| 「玩家放置」台账 | `BuildingSavedData#managed` | **是** |
| 「已固定」清单 | `BuildingSavedData#pinned` | **是** |
| 「正在倒计时」队列 | `BuildingSystem.PENDING`（`Long2LongMap`） | 否 |

倒计时队列**故意不持久化**：服务器重启后，那些还没落定的方块就地保住。
为「卡顿时的半截状态」买单不划算，玩家重放一块即可。

## 八、配置文件

| 配置项 | 默认 | 说明 |
| --- | --- | --- |
| `building.enabled` | true | 总开关 |
| `building.delayTicks` | 40 | 坠落前延迟（tick），2 秒 |
| `building.consumeSlimeBall` | true | 固定时是否消耗粘液球（创造始终不消耗） |
| `building.creativeImmune` | true | 创造 / 旁观玩家放置的方块是否豁免 |
| `building.showParticles` | true | 倒计时中的方块是否冒粒子提示 |
| `building.excludedBlocks` | `[]` | 额外排除的方块 ID |

## 九、代码地图

| 包 | 类 | 职责 |
| --- | --- | --- |
| building | `BuildingSavedData` | 「玩家放置」+「已固定」两份台账，`SavedData` 持久化 |
| building | `BuildingSystem` | 判定、倒计时队列、坠落、连锁向上 |
| events | `BuildingEvents` | 放置 / 挖掘 / 爆炸 / 粘液球 / 逐 tick |
| lang | `building.wulingdiguo.*` | 悬空提醒、固定成功 |

## 十、可能的后续

- **活塞推动**：活塞推走的方块不会触发 `BreakEvent`，链条会断在那里。
  要补齐得自己盯活塞事件，目前没做。
- **坠落体落地后不再受管**：落地位置没写回台账，所以落定之后的方块再被抽掉支撑不会掉。
- **台账只增不减**：只在「玩家挖掘 / 爆炸」时划账，被替换成别的方块的条目会留到下次。
  规模上无害（十万块约 2~3 MB），真到百万级再考虑按区块分片。
- **粘液球一次固定一片**：用户选了单块，没做「整栋一起固定」。

# 第十九章 锻造品质（武器 / 工具 / 护甲，0.4.2）

> 用户口径（2026-10-11）：
> 「加入新系统：武器品质系统，品质分类与灵珠一样，凡品=原版武器、极品接近武灵产物但还差一截，
> 一般人制造的一般都是凡品，少数有高阶的武器，铁匠（火武灵灵师）随着等级的提升锻造出更好装备的概率大大提高
> （比如合金期基本上锻造出来的都是上品）」
>
> 追问后确定：①覆盖**武器 + 工具 + 护甲**；②「工作台合成即可」，不另加界面；
> ③非火武灵玩家**也有概率但低很多**；④**不给附魔加成**（只加属性）；
> ⑤**铁匠不是 NPC，就是玩家本人** —— 持火武灵的玩家即铁匠。

## 一、规则

| | |
| --- | --- |
| 触发 | 玩家在**工作台合成**出武器 / 工具 / 护甲 |
| 掷骰 | 按合成者的武灵境界查权重表 |
| 凡品 | **= 原版数值**：不写 NBT、不加属性、不发提示 |
| 良品以上 | 写 NBT 标记 + 挂属性修饰符，并在 tooltip 名字下加一行「锻造品质」 |
| 谁是铁匠 | **持火武灵的玩家本人**；其它武灵按境界折算，没开武灵一律凡品 |

## 二、数值锚点：「极品接近武灵但差一截」

```
最终倍率 = 1 + (同材质武灵倍数 - 1) × 品质系数
品质系数：凡 0 / 良 0.2 / 优 0.4 / 上 0.6 / 极 0.85
```

同材质武灵倍数（与 `WuLingRealm` 一致）：木 3 / 石 4 / 黄金 8 / 玄铁 9 / 钻石 11 / 下界合金 14。

| 材质 | M | 原版剑 | 良 | 优 | 上 | 极品 | 武灵同款 | 极品/武灵 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 木 | 3 | 4 | 5.6 | 7.2 | 8.8 | 10.8 | 12 | 0.90 |
| 石 | 4 | 5 | 8 | 11 | 14 | 17.8 | 20 | 0.89 |
| 金 | 8 | 4 | 9.6 | 15.2 | 20.8 | 27.8 | 32 | 0.87 |
| 铁（玄铁） | 9 | 6 | 15.6 | 25.2 | 34.8 | 46.8 | 54 | 0.87 |
| 钻石 | 11 | 7 | 21 | 35 | 49 | 66.5 | 77 | 0.86 |
| 下界合金 | 14 | 8 | 28.8 | 49.6 | 70.4 | 96.4 | 112 | 0.86 |

（M = 同材质的武灵倍数，剑的攻击力为游戏内显示值 = 修正值 + 玩家基础 1。）

⚠️ **为什么是「1 + (M-1)×k」而不是「M×k」**：木剑的武灵倍数只有 3，
乘 0.25 只有 0.75 —— 良品会比原版还弱。现在这个写法保证凡品严格等于原版、各档单调递增。

| 原版 | 木/皮革 | 石/锁链 | 黄金 | 铁 | 钻石 / 海龟壳 | 下界合金 | 三叉戟 |
| --- | --- | --- | --- | --- | --- | --- | --- |
| 武灵倍数 | 3 | 4 | 8 | 9 | 11 | 14 | 14（攻击 8 与下界剑同级） |

## 三、谁掷得出好货

**火武灵**用自己那一档的权重表；**其它武灵**先把境界除以 `smith.foreignDivisor`（默认 3）再查表；
**没开启武灵**的一律凡品。

| 锻造等级 | 凡 | 良 | 优 | 上 | 极 |
| --- | --- | --- | --- | --- | --- |
| 木 | 88 | 10 | 2 | 0 | 0 |
| 石 | 80 | 14 | 5 | 1 | 0 |
| 黄金 | 68 | 19 | 10 | 3 | 0 |
| 玄铁 | 54 | 22 | 16 | 7 | 1 |
| 钻石 | 36 | 23 | 22 | 14 | 5 |
| 下界合金 | 12 | 16 | 24 | **30** | 18 |
| 绿宝石 | 3 | 8 | 17 | 36 | 36 |

- 下界合金期：凡品只剩 12%，上品 30% 为最高项 → 对应「合金期基本上锻造出来的都是上品」。
- 非火武灵的绿宝石期按黄金期查表（凡 68%） → 对应「一般人制造的一般都是凡品」。

## 四、为什么这样写

- **只加属性、不给附魔**（用户口径）。属性走 `ItemStack#addAttributeModifier` + NBT，
  与武灵凝聚物同一套机制（原版 `LivingEntity#handleEquipmentChanges` 自动应用），
  所以**不改原版物品类**，也不新增任何物品。
- **UUID 与武灵那套故意不同**（`QualitySmithing` 自己一组），避免同一件装备上两条修饰符互相顶掉。
  攻击力计算基数补 1（玩家基础攻击力），护甲 / 韧性补 0 —— 与 `WuLingType#empower` 一致。
- **凡品不打标记**：让「凡品 = 原版武器」字面成立，也不污染 NBT。
- **模组自己的物品一律排除**（红石装备、武灵凝聚物）：它们已有强度体系，再叠品质会乱。

## 五、已知缺口

- **弓 / 弩不参与**：1.20.1 没有任何「远程伤害」属性，弓的伤害由箭与附魔决定；
  最大耐久又不是属性、也没法在别人的物品类上覆盖 `getMaxDamage`。所以弓弩无属性可加。
- **工具的品质加成落在攻击力上**：挖矿速度在 1.20.1 不是属性（只有 `Tier#getSpeed`），
  想让镐子「挖得快」只能靠附魔，而本系统不给附魔。所以镐 / 铲的品质只提高攻击力。
- **怪物掉落 / 宝箱**暂未接入（本次只做了合成入口）。
